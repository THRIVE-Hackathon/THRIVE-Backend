## 2. 프로젝트 한 줄 이해

`LANDING`은 편도 총 6시간 이상 비행을 자주 하는 사용자가 착륙 후 다음 일정 전에 회복 상태를 파악하고, 회복 점수를 올리기 위한 행동 계획을 수행하도록 돕는 서비스다.

핵심 경험은 다음 한 문장으로 정리된다.

> 착륙 후 지금 내 몸은 몇 점이고, 다음 일정까지 무엇을 해야 하는가.

백엔드는 이 경험을 `여정(Trip)` 중심의 상태 머신, 회복 점수 계산, 회복 계획 생성, 체크 기록, 리포트 생성으로 뒷받침해야 한다.

## 3. 제품 방향

### 대상 사용자

- 편도 총 비행시간 6시간 이상인 여정을 연 3회 이상 경험하는 사용자
- 20~30대 장거리 이동자, 교환학생, 유학생, 출장자, 항공 승무원 등이 대표 예시
- 직업보다 `장거리 비행 빈도`를 기준으로 타깃을 정의한다.

### 문제 정의

- 장거리 비행 후 몸이 완전히 회복되기 전에 다음 일정이 시작된다.
- 사용자는 현재 몸 상태가 얼마나 무너졌는지, 무엇부터 해야 하는지 알기 어렵다.
- 기존 대안은 개인 노하우, 시차 앱, 항공사 안내처럼 부분적이거나 개인화가 약하다.

### 차별점

- 착륙 후 회복 구간에 무게를 둔다.
- 수면, 순환, 수분, 피부를 함께 점수화한다.
- 비행 전 예상 점수와 착륙 후 실측 점수를 비교한다.
- 경유 대기 시간을 회복 시간으로 전환한다.
- 점수 근거를 항상 공개해 임의의 건강 점수처럼 보이지 않게 한다.

## 7. 여정 상태 머신

기능명세서 기준 상태는 다음과 같다.

```text
created -> landed -> recovering -> done
```

| 상태 | 의미 | 진입 조건 | 홈 탭 화면 |
| --- | --- | --- | --- |
| 없음 | 진행 중 여정 없음 | active Trip 없음 | S1 |
| created | 여정 등록 완료, 착륙 전 | S1 완료 | S2 |
| landed | 착륙 확인 또는 착륙 시각 경과 | F-S4-01 실행 또는 landing_at 경과 | S4 |
| recovering | 실측 점수 확정, 회복 항목 생성 | F-S5-01 실행 | S5 |
| done | 일정 차질도 입력 완료 | F-S7-04 완료 | S5 배너 또는 S7 |

### 상태 관련 주의점

문서 안에 `완료` 기준이 두 가지로 보인다.

- 자동 라우팅 표: 다음 일정 시각 경과 시 완료
- 상태 변화 표: 차질도 입력 완료 시 done

백엔드 기준으로는 다음처럼 분리하는 것이 안전하다.

| 개념 | 권장 처리 |
| --- | --- |
| next_schedule_passed | 다음 일정 시각이 지났으므로 리포트 입력 배너를 보여줄 수 있는 상태 |
| done | TripResult가 저장되어 여정이 닫힌 상태 |

즉, `다음 일정 시각 경과`만으로 done 처리하면 차질도 수집이 누락될 수 있다.

## 8. 점수 체계

### 회복 점수

- 0~100점 범위의 참고 지표다.
- 의학적 진단으로 보이면 안 되며, 모든 점수 화면에 고지가 필요하다.
- 최종 점수뿐 아니라 근거를 저장하고 조회할 수 있어야 한다.

### 구성 요소

| 요소 | 비중 | 주요 입력 |
| --- | --- | --- |
| 수면·리듬 | 30 | 시차 크기, 시차 방향, 착륙 후 수면 관련 기록 |
| 순환 | 25 | 총 비행시간, 부동 시간, 걷기 기록 |
| 수분 | 25 | 저습도 노출 시간, 수분 섭취 기록 |
| 피부 | 20 | 노출 시간, 보습 여부, 자가 체감 |

현재 비중 30/25/25/20은 임시안이다. 코드에는 상수로 박기보다 설정 테이블 또는 계산 모듈의 명시적 상수로 분리해 조정 가능하게 두는 것이 좋다.

### 예상 점수 계산

입력:

- 출발 도시, 도착 도시
- 실비행시간
- 총 경과시간
- 경유 횟수
- 최장 대기시간
- 시차 크기와 방향

출력:

- estimated_score
- component penalties
- 설명 가능한 근거 목록
- 기본 또는 AI 한 줄 요약

예시 근거:

```text
기준 100점
- 총 비행 17시간, 경유 1회: 순환 -22
- 시차 8시간 서행: 수면 -18
- 저습도 노출 17시간: 수분 -13, 피부 -11
```

### 실측 점수 계산

입력:

- 예상 점수
- 기내 체크 기록
- 착륙 확인 시각

처리:

- P1 기내 체크리스트가 없으면 예상치를 그대로 실측으로 사용한다.
- 기내 기록이 있으면 수분, 걷기, 보습 등의 수행을 반영해 요소별 감점을 줄인다.
- 목표 점수는 다음 일정까지 남은 시간으로 산정한다.
- 목표 점수가 100을 넘으면 100으로 절사한다.

### 현재 점수 반영

회복 항목 체크 시:

- RecoveryItem을 completed로 변경한다.
- Trip.current_score를 score_delta만큼 올린다.
- 해당 요소의 기존 감점보다 많이 회복시키지 않는다.
- 하루 한도 초과 시 기록은 저장하되 점수는 올리지 않는다.
- 체크 해제 시 점수를 원복한다.

## 9. 회복 계획 생성 규칙

기능명세서의 규칙을 백엔드 로직으로 해석하면 다음과 같다.

| 규칙 | 백엔드 처리 |
| --- | --- |
| 총 개수 = 남은 시간 ÷ 4, 최대 12개 | next_schedule_after_minutes 기반으로 item count 계산 |
| 감점 큰 요소부터 배치 | score_breakdown의 penalty 내림차순으로 항목 생성 |
| 수면 항목은 현지 22~07시에만 배치 | destination timezone 기준 scheduled_at 제한 |
| 광 노출은 동행이면 오전, 서행이면 오후 | travel_direction에 따라 시간대 선택 |
| 한 화면 5개 초과 노출 금지 | API는 전체를 반환하되 `now`, `today`, `tomorrow` 구간화 권장 |

회복 항목 예시:

| title | component | score_delta |
| --- | --- | --- |
| 물 500ml | hydration | +3 |
| 10분 걷기 | circulation | +4 |
| 보습 | skin | +3 |
| 광 노출 30분 | sleep | +5 |

P0에서는 LLM이 계획 자체를 결정하게 하기보다, 서버의 결정적 규칙으로 계획을 만들고 AI는 설명 문구 생성에만 쓰는 편이 안전하다. 이렇게 해야 재현 가능하고 테스트하기 쉽다.

## 10. AI 적용 방침

문서상 AI 적용 지점은 6개다.

| 적용 | P0 권장 처리 |
| --- | --- |
| 예상 점수 산출 | 결정적 계산 로직 우선. AI 사용 최소화 |
| 실측 점수 보정 | 결정적 계산 로직 우선 |
| 회복 계획 생성 | 결정적 규칙 우선 |
| 레이오버 행동 제안 | P1. 규칙 기반으로 시작 가능 |
| 계획 재조정 | P1 |
| 리포트 생성 | P0/P1 경계. 기본 문구 fallback 필수 |

백엔드 원칙:

- AI 응답 실패가 사용자 플로우를 막으면 안 된다.
- AI 출력은 저장 전 길이, 금칙어, 의료 표현을 필터링한다.
- 점수와 계획의 근거는 AI가 아니라 서버 로직이 보장한다.
- AI 프롬프트에는 이메일, 비밀번호, 민감정보를 넣지 않는다.
- 기저질환은 입력받지 않는다.

## 13. 개인정보와 법적 리스크

이 서비스는 웰니스 서비스로 유지해야 한다.

필수 원칙:

- 기저질환을 입력받지 않는다.
- 의료적 진단, 처방, 질환별 조언을 제공하지 않는다.
- 점수는 참고 지표임을 모든 점수 화면에서 표시한다.
- 비밀번호는 반드시 해싱해 저장한다.
- AI 프롬프트와 로그에 개인정보를 최소화한다.
- 회원 탈퇴 시 User, Profile, Trip, RecoveryItem, DailyCondition, TripResult 등 관련 데이터를 삭제하거나 복구 불가능하게 익명화해야 한다.

민감해질 수 있는 데이터:

- 성별, 연령대
- 컨디션 점수
- 회복 행동 기록
- 일정 차질도

기저질환은 문서에서 명시적으로 삭제된 입력이다. 다시 요구사항에 들어오면 별도 동의, 보관, 접근 통제, 의료기기 오인 리스크를 재검토해야 한다.

## 14. 백엔드 구현 우선순위

### 1차 구현

1. 프로젝트 기본 구조, DB 연결, 마이그레이션
2. User, Profile, City 모델
3. 회원가입, 로그인, 세션 유지
4. 도시 seed 데이터와 시차 계산
5. Trip 생성, 6시간 검증, 진행 중 여정 1건 제약
6. 예상 점수 계산과 score_breakdown 저장

### 2차 구현

1. 착륙 확인 API
2. 실측 점수와 목표 점수 계산
3. 회복 계획 생성
4. 회복 항목 조회, 완료, 취소
5. current_score 반영과 하루 한도 처리
6. 하루 컨디션 입력

### 3차 구현

1. 여정 목록과 리포트 조회
2. 일정 차질도 저장
3. Trip done 처리
4. 프로필 통계
5. `.ics` 캘린더 내보내기
6. AI 문구 생성과 fallback

### 이후 구현

1. 기내 체크리스트 오프라인 동기화
2. 레이오버 가이드
3. 같은 연령대·성별 비교 통계
4. 다음 여정 개선안
5. 회원 탈퇴 전체 데이터 삭제

## 15. 백엔드가 먼저 확인해야 할 미해결 질문

### 착륙 시각 입력 문제

자동 라우팅은 `착륙 시각 이전/경과`를 기준으로 하지만, S1 입력에는 출발 일시나 착륙 예정 일시가 명확히 없다.

백엔드에는 최소 하나가 필요하다.

- 출발 일시 + 총 경과시간
- 착륙 예정 일시
- 사용자가 직접 누르는 착륙 확인만 사용

현재 스펙만으로는 정확한 자동 라우팅과 `next_schedule_at` 계산이 어렵다.

### 다음 일정 시각 계산

S1은 `착륙 후 몇 시간 뒤인지`를 입력받는다. 따라서 `next_schedule_at = landing_at + next_schedule_after_minutes`가 되어야 한다. `landing_at`이 없으면 다음 일정 시각도 확정할 수 없다.

### done 상태 정의

다음 일정 시각이 지났다고 바로 done 처리할지, 일정 차질도 입력 후 done 처리할지 결정이 필요하다. 백엔드 권장은 `TripResult 저장 후 done`이다.

### 점수 산식 확정

30/25/25/20 비중은 임시안이다. 실제 감점 구간표, 최저점, 시차 방향별 차등, 경유 가중치가 필요하다.

### 회원 탈퇴 삭제 방식

기능명세서는 전체 삭제를 요구한다. 통계 비교 기능을 유지하려면 완전 삭제와 익명화 중 어느 쪽인지 정책 결정이 필요하다.

### 캘린더 내보내기 범위

S2와 S5 모두 `.ics`를 요구한다. 하나의 파일에 여정/회복 항목을 모두 담을지, 예상 일정과 회복 계획을 분리할지 결정이 필요하다.

## 16. 설계상 권장사항

- 화면 ID가 아니라 도메인 이벤트 중심으로 API를 설계한다.
- 점수 계산은 순수 함수에 가깝게 분리해 테스트 가능하게 둔다.
- 점수 결과는 최종 점수만 저장하지 말고 근거 JSON을 함께 저장한다.
- AI는 핵심 계산보다 문구 생성에 제한적으로 사용한다.
- 모든 mutation은 인증된 user_id 기준으로 권한을 검사한다.
- 진행 중 Trip은 user_id 기준 partial unique 제약 또는 트랜잭션으로 막는다.
- 시간은 DB에 UTC로 저장하고, 화면 표시와 회복 계획 배치는 도착지 timezone으로 계산한다.
- P1 오프라인 동기화는 client_event_id 기반 idempotency가 필요하다.
- 의료 표현과 개인정보 로그를 초기에 막아야 후반에 수정 비용이 커지지 않는다.

## 17. 백엔드 관점 최종 요약

이 프로젝트의 백엔드는 단순 CRUD보다 `여정 상태`, `회복 점수`, `회복 계획`이 핵심이다.

가장 중요한 모델은 `Trip`이며, Trip은 다음 흐름을 가져야 한다.

```text
여정 등록
-> 예상 점수 계산
-> 착륙 확인
-> 실측 점수 계산
-> 회복 계획 생성
-> 회복 항목 체크로 현재 점수 상승
-> 일정 차질도 저장
-> 리포트와 누적 통계 생성
```

초기 구현은 AI를 많이 붙이는 것보다, 재현 가능한 점수 계산과 상태 전이를 먼저 안정화하는 것이 중요하다. AI는 요약, 이유, 개선안처럼 실패해도 대체 문구로 넘길 수 있는 영역부터 붙이는 것이 좋다.
